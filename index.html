HYPOTHESIS 01 · 사전 기준 충족

목적지 알람은
오전에 주로 울릴까요?

팀 안에서도 아침과 저녁으로 사용 시간대가 갈렸어요. 최초 알람 울림의 50% 이상이 오전에 발생하면 가설을 지지하기로 정했어요.

사전 기준50%
오전 발생70.0%

367건 중 257건이 오전에 발생했어요.
이 관찰 기간의 최초 울림은 오전에 집중됐고, 사전에 정한 기준을 충족했어요.

어떻게 측정했나요? ＋

8월 1일–9월 29일, 대한민국의 Android·iOS 알람을 대상으로 Firebase Analytics의 destination_alarm_ringing_started 이벤트를 분석했어요. retry_attempt = 0만 포함해 재울림을 제외하고, 개발·테스트 기기 트래픽도 제외했어요.

분석 단위는 고유 사용자가 아닌 최초 알람 울림 이벤트예요. 최소 30건·권장 100건을 넘는 367건을 관찰했어요. 플랫폼별·고유 사용자별 수치는 제공된 기록에 없어 별도로 표시하지 않았어요.

무엇을 배웠고, 어디까지 알 수 있나요? ＋

전체 울림의 46.3%가 오전 6–8시에 집중됐어요. 오전 사용 경험을 우선 살펴볼 근거가 생겼어요.

다만 한 사용자가 여러 날 사용한 이벤트가 포함될 수 있어, 사용자 70%가 오전에 사용한다는 의미는 아니에요. 시간대만으로 기상·출근·등교 목적이나 루틴 형성을 확인할 수도 없어요.

다음 질문 평일과 주말의 사용 패턴을 비교하고, 사용 목적은 별도 조사로 확인하려 해요.

HYPOTHESIS 02 · 초기 관측 / 추가 검증

함께하는 미션은
더 잘 완수될까요?

10월 14일–29일, 알람 사용 당시의 모임 참여 상태별 성공률을 비교했어요. 모임 참여 상태에서 더 높은 성공률이 관측됐어요.

미참여 · 2/728.6%
참여 · 33/5164.7%

참여 상태 33/51건, 미참여 상태 2/7건 성공.
미참여 관측이 7건으로 적어, 모임의 효과가 검증됐다고 결론 내리기에는 부족해요.

사전 기준과 관측의 차이 ＋

9월 성공률 15.1%에 5%p를 더한 20.1%를 모임 참여자의 성공 기준으로 정했어요. 관측값 64.7%는 이 기준보다 44.6%p 높아요.

하지만 과거 기준을 넘었다는 사실만으로 같은 기간의 혼자 사용한 경우보다 효과가 있다고 판단할 수는 없어요. 집단별 사용자 수와 사용자별 반복 사용 분포도 제공되지 않아, 독립 표본으로 가정한 통계적 유의성은 주장하지 않아요.

판단을 보류하고 측정부터 고쳤어요 ＋

첫 관측(10월 5일–15일)에서는 재울림이 미션 시작으로 중복 수집됐고, 나중에 모임에 가입한 사용자의 과거 사용도 참여 그룹으로 묶일 수 있었어요. 비교 그룹도 시작 1회에 불과해 결과 판단에서 제외했어요.

재울림과 알람을 구분하고, 알람 사용 당시 모임 참여 상태를 수집하도록 측정을 수정했어요. 코드의 이벤트 전송뿐 아니라 GA 맞춤 측정 기준 등록까지 확인해야 한다는 점을 배웠어요.

다음 액션 두 상태의 관측을 더 쌓고, 사용자 특성과 사용 목적이 다른지도 살펴볼 계획이에요.

출처: 팀이 공유한 Firebase Analytics·GA 실험 기록. 비율은 알람/미션 사용 건수 기준이며 고유 사용자 비율이 아닙니다. 모임 미참여 성공률은 기록 내 불일치가 있어 성공 2건 / 사용 7건으로 계산한 28.6%를 사용했습니다.

당연한 아침 뒤, 당연하지 않은 기술.

정해진 순간에 울리고, 이동을 확인하고, 신뢰할 수 있도록.

01
RELIABILITY · 가상 사례

같은 시각에 몰리는 알람 요청

오전 7시, 동시에 시작되는 하루. 요청이 몰려도 미션이 안정적으로 시작되도록 처리 경로를 개선했어요.

문제와 해결 과정 보기 ＋

문제 정각에 집중된 요청으로 응답 지연과 중복 미션이 발생하는 상황을 가정했어요.

접근 중복 요청 처리 기준과 DB 인덱스를 점검하고, 부하 테스트로 병목을 확인했어요.

가상 결과 동일한 테스트 조건에서 p95 응답 시간 820ms → 190ms. 실제 환경에서는 재측정이 필요해요.

↗
02
LOCATION · 가상 사례

“도착”을 판단하는 정확한 기준

GPS는 언제나 정확하지 않으니까. 위치 오차와 배터리 사용량 사이에서 도착 판정 기준을 고민했어요.

문제와 해결 과정 보기 ＋

문제 실내와 고층 건물 주변의 위치 오차로 잘못된 도착 판정이 생기는 상황이에요.

접근 위치 정확도와 연속 측정값을 함께 검토하고, 이동 중에만 측정 주기를 조정하는 방식을 실험했어요.

다음 검증 기기·장소별 오탐률과 배터리 소모량을 함께 측정할 계획이에요.

⌖
03
OBSERVABILITY · 가상 사례

문제가 생겼을 때, 원인을 찾을 수 있도록

미션 시작부터 도착까지의 흐름을 연결해, 사용자 경험 뒤에 숨은 오류를 추적하는 구조를 고민했어요.

문제와 해결 과정 보기 ＋

문제 여러 처리 단계에 나뉜 로그만으로는 실패한 요청의 흐름을 파악하기 어려웠어요.

접근 요청 식별자로 로그를 연결하고 지연·실패 지표를 대시보드에서 확인하는 예시를 구성했어요.

다음 검증 장애 재현 시나리오로 탐지와 원인 파악에 걸리는 시간을 확인해요.
